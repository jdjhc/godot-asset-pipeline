# Godot Asset Pipeline

Use the `asset_pipeline_*` MCP tools to read and modify production history. The Godot editor's **资产工坊** uses the same project-local backend. If the tools are not loaded, invoke the installed `addons/asset_pipeline/backend/server.py --project <project> --call <method> --params '<JSON>'` diagnostic interface with properly quoted arguments. Backend startup and installation are documented in the package README; do not inspect credential files.

## Optional concept-video layout reference

When the user supplies a concept video and requests its last frame as image input, extract the **last decodable frame** to a lossless image. Use the media file itself, not a player screenshot or an approximate end seek. Preserve the source video and record its project-local path or stable source location, content hash, decoded frame index (state its indexing convention), presentation timestamp/time base when available, image dimensions, and extraction method. Do not invent missing frame or timing metadata.

Import the extracted image as a `reference` through the same backend used by Asset Workshop, with the source video and extraction provenance attached using supported metadata or a linked sidecar. Preserve the original overall concept and its provenance. Keep the user's intended role explicit: the frame can be an assembly layout reference, or an actual image input to subject and view generation when the user chooses that workflow.

For actual generation input, set the batch's optional ordered `image_reference_inputs` once, using an edge such as `{"node_id":"accepted_video_frame","role":"layout_reference"}`. The backend appends these shared image references to each newly created subject/front/right/back stage after that stage's own inputs; do not wire the stages individually. The original concept supplies appearance, the generated subject and front view maintain asset identity, and the frame supplies the user-accepted spatial/proportion context. Write prompts against the real ordered inputs and explain this division: output one isolated asset or its requested elevation, without neighboring assets, street layout, dimension lines, labels, or video overlays. A whole-scene frame is supplementary context for image generation, never a substitute for an isolated front/right/back view sent to the 3D model endpoint. Read [the batch contract](references/batch.md) for ordering and adoption rules.

This is input preparation, not an extra agent review gate inside the automatic batch. Adopting a frame or changing dependencies does not itself request paid regeneration. Existing-node adoption preserves historical recipes; deliberately editing an existing recipe must expose affected old results as stale, not rewrite their recorded input versions to pretend they used the frame. Reuse prior assets and tasks until regeneration is within the user's requested scope.

## Submit one asset brief

Read `asset_pipeline_snapshot` first and verify its project matches the user's open project. Reuse existing subject nodes and outputs instead of generating duplicates. Inspect the concept once, identify reusable subjects, and write each subject's description and prompts, including approximate size, orientation, and known versus inferred surfaces. Do not invent original prompts for imported references. Keep future placement relationships in the asset brief and later `instance.record` records, not unsupported provider parameters.

For whole-asset production, use `asset_pipeline_create_batch` with one spec. The backend, not the agent, expands the subject/view/model nodes before any generation. Read [the batch contract](references/batch.md) for the spec. Preview once with `asset_pipeline_plan_batch`, then start the authorized batch once with `asset_pipeline_run_batch`. The backend automatically schedules dependency-ready stages, imports each result, and publishes progress to the same snapshot used by Godot. Do not recreate the graph with a sequence of agent-side node calls, manually start each stage, or add image review gates between stages. Assess images and models after the batch finishes, then place assets in the scene.

The automatic path uses Tripo's image and 3D APIs and developer credits. The host's built-in image tool is not callable by the independent backend. Use built-in image generation only when the user chooses that mode; register the complete planned chain first and record the actual prompts and inputs when importing its outputs. Do not label such host-driven generation as an unattended backend run. Adopt earlier outputs and saved tasks instead of paying to regenerate them solely to demonstrate automation.

Node kinds: `reference` (import only), `concept` (text-to-image), `subject` / `view` (image-to-image), `multiview` (image-to-four-views), `model` (named views to 3D). Dependencies are `inputs:[{node_id,role}]`. For individual views use `front`, `left`, `back`, `right`; never infer view roles from array positions or filenames. Include multiple subject/front references when they actually inform a generated side view. Each output version records the exact upstream versions used.

Importing directly is intentional: visual quality is assessed during assembly. Each version records the exact input versions used, and older results remain available when a stage is repaired.

## Continue or repair a run

Batch progress is available in `snapshot.batches`; individual jobs retain their remote task IDs. `asset_pipeline_pause_batch` pauses local scheduling/polling, not remote billing. `asset_pipeline_resume_batch` continues remaining work and polls existing task IDs. Failed or ambiguous paid submissions must not be blindly repeated. Resolve the reported stage failure before authorizing a fresh attempt. The user has already authorized the asset scope when asking to generate it; do not ask again for each stage within that scope.

For a targeted repair after the final review, run only the needed stage:

Call `asset_pipeline_plan` before a new submission to inspect roles, parameters, missing/stale upstream inputs and affected descendants. Preview never uploads or spends credits. Editing a node marks descendants stale but does not regenerate them. Stale versions remain usable intentionally; do not silently replace them with unrelated results.

`asset_pipeline_run` submits ONE selected node and uses Tripo **developer API credits**, independently of Studio membership. Follow the user's already authorized scope and budget; do not turn a request for one asset into a batch of retries. Stop on unexpected cost/scope or unusable output and explain the specific result. Use `asset_pipeline_resume` for a saved job ID; it only polls/downloads the existing remote task. An ambiguous submission must be reconciled using its remote task ID (`asset_pipeline_attach_task`), never blindly resubmitted. Pausing local polling does not cancel remote billing.

Current transport supports installed `tripo-cli@0.5.1`, using its official client with submission retries disabled. Provider status is local and does not prove account balance or API availability. Image and model endpoints expose different options: model and multiview endpoints do not accept a freeform prompt. Preserve the visual prompt on the image stage. Prefer self-contained GLB for direct Godot import; quad mode can return FBX plus external textures/archives which require additional handling.

## Assemble and repair

Use the existing Godot Scene Bridge skill/tools for live editor inspection, reversible transforms, selection, asset instances and rendered previews. The Asset Pipeline panel can also place a selected model version inside a stable Node3D wrapper. Keep wrapper transform and manual children when replacing its generated child. Do not replace every scene instance merely because a new library version exists; instances stay pinned until explicitly updated.

When editing through the scene bridge, record the successful scene/node path, asset node ID and version via `asset_pipeline_record_instance`. Scene metadata is the source of truth after native Undo/Redo; database instance entries are last-known observations, not automatic scene subscriptions. Complete the concept-camera check below before judging placement. Diagnose whether a remaining problem is geometry, reference image or placement, and rerun the earliest stage that actually needs change. Keep old outputs available for comparison/rollback. Saving scenes remains a separate operation.

## Match the overall concept camera before final review

After the production batch finishes and the assets are assembled, reopen the **original overall concept image** from the dependency graph. Match its viewpoint before accepting the layout; an attractive arbitrary overview or individual model turntable is not this check. This is a final assembly step, not a gate between generation stages. If a user-accepted video layout reference exists, review it alongside the original concept-camera capture and save a corresponding layout overview. Use the accepted layout for intended positions, spacing, and facing; distinguish intentional changes from placement errors. Do not reject that layout solely because it adds or changes space unseen in the original concept, or force an exact reconstruction of unobserved space. Treat generated dimension labels as proposed design values, not measurements, unless independently established.

- Infer perspective versus orthographic projection, camera position/height, yaw/pitch/roll, field of view or orthographic size, and framing from the horizon, vanishing lines, and recognizable scene landmarks. Match the reference's aspect ratio and crop. A single image generally does not determine a unique physical camera; label the result as an estimated match rather than an exact recovered pose.
- Establish the camera using stable anchors such as road intersections, building corners, and ground-contact points distributed across the image. Resolve camera/framing errors before moving assets to compensate for them. Then compare the subjects' screen positions, relative sizes, spacing, facing directions, depth order, occlusion and contact with the ground.
- Render the **actual Godot scene** from that matched camera and inspect the screenshot alongside the overall concept. Read the capture tool's current schema: position and target alone do not specify lens, projection or roll. If these controls are absent, use an available engine rendering workflow that renders the configured Camera3D; do not describe a default-lens capture as a matched-camera check. Do not use image generation to manufacture the verification screenshot.
- Correct placement errors and capture again from the same reference camera. Revisit the camera only when the comparison supports a camera error. If the reference has inconsistent perspective or unavailable geometry prevents a meaningful match, record the visible mismatch and uncertainty rather than forcing a false match or silently regenerating paid assets.
- Save the final screenshot and camera settings (scene path, reference node/version or source path, projection, transform, FOV/size, and image dimensions/crop) with the assembly artifacts so the comparison can be repeated. Show the reference-matched result and report remaining placement issues before calling the scene verified; a separate overview may accompany it.
